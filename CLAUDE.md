# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Content schema, validator and a deterministic battle engine (Step 1 vertical slice) for a tactics auto-battler. Game content lives as YAML in `content/`; TypeScript (zod v4) defines the schema and a layered validator checks it. Design intent is in `docs/design_doc_v2.md` (tags: **[DECIDED]** / **[DEFAULT]** tunable / **[OPEN]**) and authoring templates in `docs/templates_v2.md`. When docs and `src/schema/` disagree, **the schema wins**. `docs/conversion_report.md` tracks designer decisions applied and questions still open.

## Commands

```bash
npm run validate                                   # validate ./content at official tier
npm run validate -- content --tier=community --strict   # community tier; --strict fails on warnings
npm run validate -- content --json                 # machine-readable report (--verbose shows info notes)
npm test                                           # node:test suite via tsx
node --import tsx --test --test-name-pattern="duplicate id" test/*.test.ts   # single test
npm run typecheck
npm run schema:export                              # regenerate schemas/*.schema.json from zod
npm run sim -- content/battles/sample.yaml [--json] [--pp-active=N] [--pp-passive=N] [--formula=ratio:150]  # validate a battle input, run up to 3 phases, print the log (or JSON events)
npm run editor                                     # local editor (Vite, http://127.0.0.1:5173): tactics board, validation, breakdown, run sim, save
EDITOR_PORT=5180 npm run editor                    # same on another port (default 5173; the API's host/origin guard follows it)
npm run editor:build                               # static editor build (content bundled, runs in the browser) into editor/dist (gitignored), deployed to GitHub Pages
npm run batch -- content/battles/*.yaml [--runs=100] [--seed=1] [--json] [--pp-active=2,3,4] [--pp-passive=2,3] [--formula=subtract,ratio:100,scaled_subtract:20]  # N seeded runs per battle file, aggregated balance report; PP / formula lists = a sweep (summary row per combination + the first combination's full report)
```

`npm run typecheck` covers the editor too (`tsc -p editor` for the browser code). CLI exit codes: 0 ok, 1 errors (or warnings with `--strict`), 2 load failure (missing file / bad YAML). There is no build step for the engine (`noEmit`; everything runs through `tsx`); only the hosted editor is built (`editor:build`, `.github/workflows/pages.yml` on push to main). `schemas/` is generated output — regenerate with `schema:export` after schema changes rather than editing it.

## Architecture

Validation pipeline (`src/validate/index.ts`), each layer only sees what the previous accepted:

1. **Load** (`src/load.ts`): reads the fixed file set in `FILES` (`terrains.yaml` and `gods.yaml` optional) plus optional `content/rosters/*.yaml`. Roster files whose name starts with `defender` are validated as defenders (anchor + ban sheet required); others as challengers.
2. **Schema pass** (`validate/schemaPass.ts`): zod-parses each entry; failing entries are dropped, passing ones are indexed into a `Pack` (`validate/pack.ts`, with `byId` maps). If `rules.yaml` fails, later layers are skipped.
3. **Semantics** (`validate/semantics.ts` `checkPack`): duplicate ids across all collections, cross-references, per-type rules, and tier checks. `validate/walk.ts` (`forEachEffect` / `forEachCondition`) enumerates every effect and condition tree in the pack with its location and context — use it rather than hand-walking content.
4. **Rosters** (`validate/roster.ts`, with `cost.ts`, `eligibility.ts`, `tactics.ts`).

Issues go through a `Collector` (`src/types.ts`) with stable codes (`E_*` error, `W_*` warning, `I_*` info) and `file > id > path` locations; tests assert on these codes. Zod refinements can emit a specific code by prefixing the message with `[E_CODE] ` — `reportZod` strips it and uses that code instead of `E_SCHEMA`.

**Registries** (`src/registry/`) are the extension points:
- `conditions.ts` `LEAF_REGISTRY`: adding a condition leaf is one entry (param schema, allowed contexts `tactic` / `authored` / `ban`, `communitySafe`). Leaves referencing other content also go in `LEAF_REFS`. Hero-ID leaves are authored-only, never allowed in player tactic sheets or ban sheets.
- `effects.ts` `EFFECT_REGISTRY`: tier flag per effect type. A new effect type also needs its zod variant added to the discriminated union in `src/schema/effect.ts`. `OFFICIAL_ONLY_STATUS_FLAGS` lists status flags barred from community packs.

**Tiers**: `official` vs `community`. Community packs may only use `communitySafe` leaves/effects/status flags (design rule: anything that revives, delays/denies actions, strips buffs, changes PP, or hits the whole field is official-only).

Enums are in `src/schema/enums.ts`; tunable numeric constants (stun pushback, roll clamps, cost weights, etc.) belong in `content/rules.yaml`, not code. Cost is always computed, never authored. Hero and soldier base stats follow the stat guideline and factor table in design doc 3.3 (Decision 131).

## Engine

`src/engine/` runs a validated battle (`runBattle` in `phase.ts`); `src/formation.ts` (slot placement: row + column), `src/draft.ts` (draft) and `src/edits.ts` (between-phase edits) are shared with the validator.
- `state.ts` builds units (stats, PP, rows, formation order) and throws on a full row (`E_BATTLE_ROW_FULL`), a doubly claimed slot or a column beyond the board (`E_BATTLE_SLOT`); `BattleOptions` (last argument of `runBattle` / `preBattleState` / `createBattleState`) is the what-if knob: `pp: { active?, passive? }` replaces every hero's base PP before gear PP (cap = max(rules.pp.max, override + gear)), never part of a battle file (sim/batch `--pp-*` flags, editor PP control, api `pp` field 0..10). `stats.ts` effective stats (Section 9.1 stacking, with the INT/MDEF pairing of Decision 132: `withPairedStats` / `PAIRED_STATS` make ATK / DEF lines of skill statuses (active / passive / soldier category), leader auras (`prebattle.ts auraModifiers`) and soldier skills (`state.ts buildSquad`) also apply to INT / MDEF unless the source names that stat; never equipment, item effects, blessings or terrain) plus `applyStatus` / `completeAction` (status ticks); `timeline.ts` the scheduler and tie order; `conditions.ts` and `tactics.ts` the condition evaluator and `decideTactic`; `damage.ts` damage, heal and effect execution; `phase.ts` the phase loop, end conditions and `runBattle`; `passives.ts` hero passives; `equipment.ts` item effects; `rng.ts` seeded streams; `log.ts` typed events and the text renderer.
- Per-action call order: `nextAction` -> (a `prevents_action` status: `executePrevented` instead) -> `decideTactic` -> spend PP -> resolve effects (on_hit / on_attack effects last) -> `completeAction` -> `rescheduleOnSpdChange` -> `scheduleNext` -> `Unit.actions++`.
- Determinism: every random roll goes through the phase rng (`phaseRng`, one stream per phase from `battle.seeds`), pre-battle rolls included: `beginPhase` passes the phase stream to `runPreBattle`, and `preBattleState` (battle_setup stats, editor breakdown) a separate `phaseRng` from the same seed so the phase stream is untouched; the `createRng(0)` fallback in `prebattle.ts` is only for callers that pass none (tests). No `Date` or `Math.random` in the engine.
- Squads (2.0-2.2): `formation.ts` resolves hero slots (row: entry `preferred_row`, else the character's, else the class default, the leader is not special and may stand front or back; column: the entry's optional `column` claims exactly that (row, column), omitted fills the lowest free column of the row in roster order; `slotConflicts` finds duplicate in-range claims; `rowOverflows` = more heroes in a row than columns, while an explicit column beyond the board is only `E_BATTLE_SLOT`) and the leader's `squad_row`. `createBattleState` adds ONE squad `Unit` (`kind: "squad"`, id `squad_<leader>`) per side, with per-soldier HP in `soldiers[]` (hp/maxHp are sums); Soldiers attack and defend as one (Decision 130): `squad.ts` runs ONE attack per squad action on its own SPD schedule (one hit/crit/guard roll), and `damage.ts` sums the living soldiers' stat (`squadSize` x the per-soldier effective stat) for a squad attacker's power and a squad defender's DEF/MDEF; rate stats are never summed. Any hit on a squad (single or area, `hitSquad`) is rolled once and overflows (Decision 128): a killed soldier's raw leftover carries to the next lowest-HP living soldier until used up or the squad is wiped, never to the hero (`applySoldierDamage`: a `damage` event per soldier, `spill: true` on carried ones, ONE `after_hit` per hit with amount = the raw damage, as for heroes, and lost = total HP removed, which reflect reads). Heroes-only helpers (`livingOf`, `alliesOf`) drive wipe/exhaustion/idle checks; `targetsOf` includes the squad. Soldier skills are `Unit.innate` modifiers (category `soldier`) read by `statBreakdown`.
- Events (2.3): `events.ts` is a synchronous bus (`state.bus`, one per phase): before_hit, after_hit (landed hits only), after_heal, after_action, on_death (hero or squad wipe), phase_start. Hit payloads carry damageType / range / single. `EVENT_SPECS` maps every content event name (EVENT_NAMES) onto a bus event with one predicate, shared by passive triggers and the matching condition leaves (in an event context they judge that event; outside one they read the unit's window of `bus.history` since its last after_action, `windowOf`). Handlers have an owner (null = engine) and an `order`; dispatch is by (order, registration). The bus enforces per-hit-once centrally: a handler fires once per attacking action (`bus.beginAction()`) per affected unit, and every fire is logged as a `trigger` event. Reactions never trigger reactions. `reactions.ts` holds the until_next_hit expiry (once per action per defender) and event-triggered soldier skills (`on_hit` = after_hit when the squad hit; `on_attack` = after_action of the squad), whose effects run through `runEffect` in `damage.ts`.
- Leader rules (2.4): `leader.ts`. `state.leaders[side]` = `{leaderId, auraActive}`. Leader death (`killUnit`) removes the squad and its leader/party soldier skills, sets auraActive false and logs `leader_down`; `applySuccession` (phase start) names the first living hero of the leader line (the side's hero order: leader-line order after the draft), or the hero a challenger edit names for that phase, and restores the flag only (`leader_succession`), never the squad. `Unit.leaderUnit` makes a squad read its leader's status stat modifiers (`statBreakdown`). The leader's `stat_penalties` (Leon SPD -20) become innate modifiers when its paired soldier type matches; only the leader has a deployed squad, so only it is penalised. Soldier skills targeting `leader`/`party` (always-on `modify_stat`) become innate modifiers on those heroes. Aura content is in `prebattle.ts` (below).
- Pre-battle and auras (2.5): `prebattle.ts` holds `PREBATTLE_STEPS`, an ordered list of named steps (equipment, terrain, buff_grants, immunity, buff_removal, debuffs, event_auras, spd_finalization; equipment = item modify_stat effects and non-debuff pre_battle item effects; pre_battle passives go to buff_grants / immunity / buff_removal / debuffs by what they do, `passives.ts preBattleStepOf`; negative aura modifiers in debuffs are blocked by Immunity) that `beginPhase` runs after succession and before `scheduleInitial` (also for the phase-1 setup stats). Only a side's current leader with `leaders[side].auraActive` has an aura. Always-on `modify_stat` aura effects become `passive`-category `StatusInstance`s with `inline` modifiers (`aura:<leader>:<n>`, never ticked) on the targets chosen by aura side, faction and `filter` (hero_is / faction_is / party_has_hero leaves exist in the engine evaluator); `removeAuras` ends them on leader death. Event auras (Jasmine, `self_action_completed`) subscribe on the bus (order 50) and run their effects through `runEffect`. The `terrain` step puts the battlefield's modifiers (`content/terrains.yaml`, optional file) on every living hero and squad of the listed classes, both sides, as whole-phase inline instances in the `terrain` stacking category (`terrain_applied`; a squad never shares its leader's terrain). Logged as `aura_applied` / `aura_removed` / `trigger`; unsupported aura effects as `not implemented: aura ...`. Only hero actions count toward `max_actions_per_phase`; squad actions have a separate bound (10x). Battles: `sample.yaml` (2v2) and `full4v4.yaml` (2v2 with all four heroes; a true 4v4 is built from clones in `test/engine.fullbattle.test.ts`, content has only 4 heroes). Tests default to auras off (`loadReal({ auras: true })` keeps them).
- Passives (3a): `passives.ts`. Only passives enabled on the hero's tactic sheet run (design 4); tactic activation ?? default_activation is checked when the trigger fires. on_event passives subscribe on the bus (order 30; hit events use trigger_timing), while_condition passives are re-checked by `checkStatePassives` after every damage, heal and action and in pre-battle (spend on activation, end with their statuses when the condition ends, spend again on return), pre_battle passives fire in their design-9 pre-battle step (above). Each trigger spends pp_cost once; short PP logs `passive_blocked`. Several passives on one event resolve in the hero's skill order. Passive statuses use the `passive` category. reduce_damage `this_attack` (Quick Guard) lives on `bus.reductions` until the action ends and multiplies with guard under the cap. Cover (Decision 116): the `cover` effect in a before_hit passive sets `redirect` on a single-target hit aimed at an ally hero; `rollOutcome` logs `cover` and resolves the hit on the coverer (no content uses it yet).
- Statuses (3a): `applyStatus` (stats.ts) blocks debuffs (`DEBUFF_CATEGORIES`) on a unit with a blocks_debuffs status (`status_blocked`) and stores nothing for `instant` ones. Stun (`delays_pending_action`): `timeline.ts delayPending` adds `rules.stun_pushback_counts` to the pending entry (`TimelineEntry.delay`, unscaled by SPD changes; with no entry it waits in `Unit.pushback`), logged `action_delayed`. Fairy's Grace (`intercepts_death`): `applyDamage` / `applySoldierDamage` revive at the percent (`death_intercepted`). Regen (`heals_on_hit_percent_max_hp`) and `removes_on_hit` are after_hit engine handlers in `reactions.ts` (once per action per defender). Confusion (`ignores_tactics`): `decideTactic` picks the first affordable damage skill on a random target (`random_any` = any side); squads attack random units. `until_used` statuses end when their flag is used (`useStatus`). `remove_buffs` strips `buff`-category dispellable statuses. A while_condition status keeps the applying skill's activation (`whileCond`) and ends when it turns false (`checkStatePassives`).
- Library (3a): every LEAF_REGISTRY leaf evaluates (`conditions.ts` header lists the [DEFAULT] meanings; ban leaves read the hero, `Unit.cost` is its roster cost); selectors take an optional `side` and PP metrics. `damage.ts runEffect` runs every effect type: an effect `condition` filters targets; hero skill `on_hit` / `on_attack` effects run after the others on the units the action hit; `modify_pp` (clamped, `once_per_attack` via `bus.ppOnce`, `pp_change`); `delay_action` / `advance_action` (`action_moved`); reduce_damage durations this_attack / next_hit / until_next_action / phase (`Reduction.until`). `prevents_action` loses the action (`action_prevented`, only the preventing statuses tick). `use_limit` / `cooldown` (per phase, cooldown in own actions; `tactics.ts skillReady` / `recordSkillUse`) apply to actives and passives.
- Equipment (3b): `equipment.ts`. Equipment type standard (Decision 133): an item has exactly one type tag (`E_EQUIP_TYPE`; accessory categories gloves / boots / ring / ... , only weapon, armor and shield types are gated by the hero's `equipment_tags`) and its flat stat lines are `rules.equipment_bases[type]` (`src/equipmentBase.ts equipmentStats`, shared by the engine, cost, draft and editor); items author no stat lines. The type's base goes into `Unit.equipFlat` and `pp_modifiers` into the PP pools (capped at `rules.pp.max`) when `state.ts` builds the unit; `Unit.equipment` holds the worn ids (duplicate accessories are a roster-validator rule; their flat lines add). `registerEquipment` sorts item `effects` into `state.equipment`: always `modify_stat` -> `equipment`-category inline instances (`equip:<item>:<slot>:<n>`, `equipment_applied` / `equipment_removed`), put on in the equipment pre-battle step and, when conditional, re-checked by `checkEquipment` with the state passives (same category, so equipment vs equipment never stacks; not shared with the wearer's squad); `on_hit` / `on_attack` -> run in `executeSkill` after the skill's own on-hit effects, as reactions (Longinus); `pre_battle` -> `runPreBattleEquipment` in the equipment / buff_removal / debuffs step (`equipStepOf`; Strange Box Confusion is a debuff). Other effects are build notes `not implemented: equipment ...`.
- Devotion (3c): `src/devotion.ts` (shared) turns a hero entry's `sigils` (god per filled slot) into unlocked blessing tiers (`Unit.blessings`; 2 = two_piece, 4 = both); `equipment.ts` runs them with the item machinery: modify_stat -> `prayer`-category instances `prayer:<god>:<tier>:<n>` (`blessing_applied` / `blessing_removed`), `ignore_guard` judged at roll time (`ignoresGuard`), `reflect_damage` / `on_event` effects as after_action reactions over the action's hits on the wearer (`bus.actionStart`), reduce_damage battle as a pre-battle reduction. `executeSkill` sets `bus.singleAttack` (leaf `action_is_single_target`) and re-checks modifiers before the rolls. Blessing HP percent raises max HP (`state.ts`); cost: `cost.ts effectPrice`.
- Class traits (3d): flyer defender EVA x(1 + `class_traits.flyer_melee_eva_bonus`/100) vs melee hits (`hitChance`); aquatic SPD +`aquatic_water_spd_bonus`% on `water` terrain in the terrain pre-battle step (`terrain:<id>:water`).
- Slice scope: hero skills, passives, statuses, equipment, devotion, class traits and the condition library (above), up to 3 phases. Everything else (non-stat/non-heal auras, soldier skills beyond on_hit/on_attack and always-on modify_stat, effect triggers that do not fit their skill) is **not implemented**: it is logged as `not implemented: ...` and never silently dropped. Tunables stay in `content/rules.yaml`.

- Batch (4.2): `src/batch.ts` (CLI) and `src/batchReport.ts` (`runSeeds`, pure `aggregate` over event arrays, `runMatchup`, `renderReport`; [DEFAULT] choices in its header). Each file is one matchup; run i's seeds are a hash of (base seed, file basename, i); the roster form drafts every run. Aggregates from `result.events` only. `src/cliBattle.ts` is the read/validate step shared with `sim`.

## Editor

`editor/` (roadmap Step 5 milestone 1, Decision 127): Vite + React + TypeScript, plain CSS. Two modes over one API core, `editor/core.ts` (`createCore(texts, store)`: content as texts path -> YAML, a `ContentStore` that lists / reads / writes battle and roster files; no Node imports, and everything it imports must stay browser-safe: the pure loader `src/content.ts rawFromTexts`, `src/validate/raw.ts validateRaw`, `src/options.ts` what-if parsers; `src/load.ts` / `validate/index.ts` / `cliBattle.ts` are the disk / CLI wrappers; `tsc -p editor` has no Node types, so a Node import there fails typecheck). **Local** (`npm run editor`): `editor/vite.config.ts` mounts `editor/api.ts` (`createApi(contentDir)` = the core over `content/` on disk with symlink checks and 409-on-exists saves, tested in `test/editor.api.test.ts` without Vite) as `/api/*` middleware, so the schema, validator and engine run in Node; the browser only renders. **Hosted** (`npm run editor:build` = `vite build --mode static`, base `./`, output `editor/dist`, GitHub Pages at /LO-Engine/): `client.ts` (`HOSTED` = mode static) sends the same requests in-process to the core in `editor/src/staticApi.ts`, which bundles `content/*.yaml`, `battles/` and `rosters/` with `import.meta.glob` (same shapes and error statuses, so the UI is shared); content is read-only, save validates then downloads the YAML, "open local file" loads one back, and a badge / note say so. Sprites use `import.meta.env.BASE_URL`. Core tests: `test/editor.core.test.ts`. Endpoints: `GET /api/content` (dropdown data, tactic-context leaves with their zod -> JSON Schema params, file lists), `GET /api/file?path=` (only `battles/*.yaml` / `rosters/*.yaml`), `POST /api/validate|breakdown|sim|save` with `{ battle }` (save only under `battles/`, refused with 422 + issues when the battle has errors; breakdown/sim likewise). The pack is loaded once at server start: restart the editor after editing content YAML. Saving rewrites the file with `yaml.stringify` (comments are lost). Breakdown uses `preBattleState` (engine/phase.ts, also used for battle_setup): state after the pre-battle steps of a phase, edits applied, HP not carried over. Shared shapes in `editor/apiTypes.ts` (no Node imports). The UI (`editor/src/`) keeps the battle as loose JSON, tags inputs with `data-path` = validator path so clicking an issue highlights the field. The board (`formationLayout.ts`, `Formation.tsx`) is per slot: a fixed 2x3 hero grid plus two soldier rows (`layoutSide`); dragging a hero to any hero slot writes `preferred_row` + `column` (an occupied slot swaps both), Alt+arrows step one slot (`moveEdit` / `stepEdit` / `dropKind` take a `{ row, column }` target), and the roster panel's `column` select edits the same JSON. Not editable yet: between-phase edits and the defender ban sheet (kept as loaded); skills/equipment/character editors are later milestones.

## Battle input

`content/battles/*.yaml` (schema `src/schema/battle.ts`, validated by `src/validate/battle.ts`): two fielded sides (heroes reuse roster entries, plus a `leader`), three seeds (integers in [0, 2^32)) and an optional `battlefield` terrain id (null/absent = none; damage effects' `bonus_on_terrain` applies when it matches). Stable codes: `E_BATTLE_SIZE`, `E_BATTLE_LEADER`, `E_BATTLE_DUP`, `E_BATTLE_SEEDS`, `E_BATTLE_TERRAIN` (unknown battlefield), `E_BATTLE_ROW_FULL` (a row holds more heroes than `rules.board.columns`, preferred rows applied), `E_BATTLE_SLOT` (two heroes claim the same (row, column), or a `column` beyond `rules.board.columns`; also checked per phase edit). Hero entries take an optional `column` (1..columns, omitted = auto) beside `preferred_row`; both are editable between phases. Hero-level problems use the roster codes (including `sigils`: unknown god `E_REF_MISSING`, sigil on an empty slot `W_SIGIL_EMPTY_SLOT`; sigils are locked between phases).

Roster form (3e, alongside the fielded form; recognised by `challenger.roster`): each side has a `roster` (roster schema, checked by `checkRoster` in `validate/roster.ts`: defender needs anchor + ban sheet; the defender roster's `battlefield` is the battle's), optional `draft: { bans, protects }` (human picks, consumed in `rules.draft.steps` order) and `edits`. `resolveDraft` (`src/draft.ts`) runs the steps (bans hit the other roster; anchor and protected heroes are unbannable; rule-sheet bans: rules by priority, each fires once, else fallback = highest cost, ties cost then id), orders the fielded heroes by leader-line rank (first = leader) and moves the lowest-ranked non-leader out of an overflowing row (its explicit `column` is dropped); the engine logs `draft_step` / `draft_result` before `battle_setup`. Edits (both forms, challenger only): `edits: [{ phase: 2|3, leader?, heroes: [{ char_id, tactic_sheet?, preferred_row?, column?, squad_row? }] }]` (`column: null` = back to auto; 1..columns, else `E_BATTLE_SLOT`), applied from that phase on (`battleAtPhase`), logged as `edit`. Codes: `E_DRAFT_PICKS` (pick count vs human steps), `E_DRAFT_PICK` (ineligible pick), `E_DRAFT_RESULT` (a side does not end with `fielded` heroes), `E_EDIT_LOCKED` (non-editable field, or defender edits), `E_EDIT_PHASE`, `E_EDIT_HERO` (not a fielded hero), `E_BAN_METRIC` (ban metric not `cost` / `hp` / `stat:<STAT>`), `W_ROSTER_BATTLEFIELD` (battlefield on a challenger roster, ignored). Example: `draft_city.yaml`.

## Tests

`test/validate.test.ts` works by mutating a fresh copy of the real content: `fresh()` (structured clone of `content/`), mutate, then `codes(raw, tier)` returns error codes via `validateRaw`. `roster()` in `test/helpers.ts` builds a valid 6-hero roster (cloning extra heroes). The first test asserts the real content has zero errors, so content edits must keep it valid.

## Working guidelines

- Before changing anything, the main agent lists every file needed and reads them in one pass, then hands the edits to subagents, then runs the tests once.
- The agent the user talks to never writes code or builds anything itself. It is the supervisor, responsible and accountable for all work done by the subagents it spawns to execute.
- Treat all work as a todo queue. When the user proposes tweaks, changes or corrections, append them to the queue; don't break the queue to prioritize them. Exception: a correction to the task currently in progress is applied immediately, before moving on. Only stop when the queue is truly 100% clear.
- Mistakes aren't your fault; don't apologize. A mistake means a gap or issue in the instruction files. Describe which part of the instruction files caused it and suggest the fix. Be solution oriented.
- YAGNI: don't overengineer, and never expand scope without permission. Do suggest scope improvements when they make sense. All work must be justifiable. Judge where the project sits between "quick and dirty" and "production grade" and match the engineering effort to that.
- After making changes, the supervisor (not the implementing subagent) spins up a reviewer subagent on a cheap model with minimal context to look over them with fresh eyes for possible problems. Implementing subagents are told not to spawn subagents or commit.
- Commits: once a queue item is implemented, reviewed, its review findings fixed and all checks are green (typecheck, test, validate, sims), the supervisor commits it on its own with a short message. Never push, never commit a red tree, never mix two queue items in one commit.
- Session continuity: `docs/handover.md` is the running state (done, todo queue, open designer calls). Update it at the end of every queue item so a fresh session can start from it.
